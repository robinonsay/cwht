## 1. Rules for this file

1. **What goes in.** A lesson is a fact observed while doing the project's own work that should change how later work is done. Each entry names its source artifact (a record, a package item, a log entry or a commit), so that it is evidence and not opinion (charter section 11 rule 2).
2. **Entry numbers.** Charter section 6 defines no identifier scheme for lessons, so entries are cited as `docs/lessons-learned.md` entry *n*, as the deviations log does for its entries. Entry numbers are never reused or renumbered.
3. **Append, then update the state.** New lessons are appended. The "Applied in" and "State" cells may be updated when the action lands, with the commit that applied it; the lesson text is not rewritten. A lesson found to be wrong gets a new entry that cites it.
4. **Area tags** (08 section 1 repo map: "tagged by area, for example software"): `cm` configuration management and records; `reviews` review conduct and records; `requirements`; `risk`; `safety`; `tools`; `software`; `planning` TPMs, budgets and schedules.
5. **Use at each gate.** Before each readiness declaration the package author reads this file, lists in package section 19 the entries added since the last review, and states for each whether its action was applied (S10). The PDR package section 19 lists entries 1 to 17.
