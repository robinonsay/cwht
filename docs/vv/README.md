## Workflow in one paragraph

A requirement is written with its method; an independent test author writes the case with its `Credit row:` line; an independent reviewer makes it `Active`; the conductor runs it on a configuration-managed article (tagged firmware release `release/FW-vX.Y.Z`, delivered unit) after TRR for Bench and OnAir; a report is filed here with `credit: true`; `tools/traceability.py` checks the evidence (rules of process section 7.3, implementation status in 7.4) and the requirement moves to `Verified` in the matrix; any discrepancy stops the run and opens an NCR here; the owner witnesses, dispositions and, at SAR, accepts, which moves the requirement to `Closed`. A software requirement verified by HostUnit or Emulation is `Verified` on the credited report against the tagged release; PCA-05 records the installed-release line in the unit's `adp/<unit-serial>/as-built.md` and changes no status; the requirement becomes `Closed` in the commit that records the signed SAR decision memo, and only when that PCA-05 line names the credited release (charter section 9; process section 5.3; CM plan section 7.2). Dev-board runs are supporting evidence with `credit: false` and never move a status (process section 4). Validation cases do the same against `OPS-NNN` and `MOE-NNN`, with the owner and friends as the users and both key types exercised (SI-018).

## Quick checks before committing anything here

1. `.venv/bin/python tools/traceability.py` exits 0 (the file is not executable; run it through the venv interpreter).
2. Every report and NCR has complete front matter in the parser subset (no trailing `# comments`, no nested mappings) and every cited artifact exists with the listed hash; `tools/traceability.py` checks this (rule 7.3.8: `REPORT_FRONT_MATTER`, `REPORT_ID_FORMAT`, `REPORT_UNRESOLVED`, `REPORT_ARTIFACT`, `NCR_ARTIFACT`), so run it before committing.
3. Every Bench or OnAir report names the witness and the instrument calibration performed that session.
4. Every file in a report or NCR artifact directory is listed in its `artifacts` front matter with its hash; logs are named `*.log.txt`; an LTspice `.raw` is present only when the report cites it and it is 10 MB or smaller (process section 15).
