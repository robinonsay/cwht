**Expands:** charter §2 (roles and independence), §4 item 2 (presented reviews), §5 (document tree and the single peer-review record) and §11 (working rules: search first as a hard rule, visual closure, independence, token economy, headless only), SEMP §4.1 and §5.0 (resources, responsibility, training). **Satisfies:** SWE-017 as tailored in the RMM (briefing and the required-reading table of 07 §2.2 provide training); peer-review conduct with checklists and recorded measurements (SWE-087, SWE-088, SWE-089); the training element NPR 7123.1D §3.2.1 includes in implementing each process. **Guidance followed:** SE HB App. J §5.0 (resources, responsibility and training per process), SE HB App. N (technical peer reviews and inspections). **Owner:** Claude (lead SE) maintains; Robin approves at SRR. **Aligned to:** charter commit b8214ca (2026-09-25).

Every subagent that Claude dispatches receives the standard brief block of §1 verbatim, followed by the role block of §3 for its role and the assignment block of §4. - Write the single peer-review record at the path your assignment names in FILES TO WRITE, docs/reviews/<REVIEW>/checklists/<product-slug>.md: a copy of the checklist template with every item answered Yes, No or N/A with evidence, and the YAML front matter whose single field list is docs/process/01-lifecycle-and-reviews.md section 13 (Peer review record row; the fields tools/validate_docs.py requires, including id, the INSP-NNN Claude assigns, author_agent, reviewer_agent, readiness_met and date, and assurance_reviewer_agent for the products of 07 sections 2.1.1 and 14.1). Each finding appears in the body under an anchor #finding-<n> with severity and state Open. There is no peer-reviews/ folder; never create one.
```
- Return the same fields in your StructuredOutput summary (section 5) so Claude can check them against the file.
```

**Review record.** The filled checklist `docs/reviews/<REVIEW>/checklists/<product-slug>.md` is the single peer-review record for its product, where `<REVIEW>` is the next gate the product feeds and the slug is `<type>-<product-stem>` (01 §13; charter §5). Its front matter follows the single field list of 01 §13 (the fields of the `tools/validate_docs.py` built-in record schema). There is no separate `peer-reviews/` folder, and `validate_docs.py` fails if one exists. Claude assigns the next free `INSP-NNN` in the assignment block; INSP numbering is audited from the front matter of the `checklists/` files, which `validate_docs.py` checks for uniqueness across all reviews.

A review that needs a checklist that does not yet exist is not held; Claude writes the checklist first, and there is no "by reading" substitute, because the record's `checklist` field must name an existing template. The four due items above (`analysis`, `software-assurance`, `visual-product`, `safety`) are the only missing checklists. SRR product types with a checklist today: requirements (requirements checklist sections A to F); expectations, ConOps and the concept (sections A, B, F); plans, process documents and the technology assessment (section G); ICD stubs (design checklist section I); ADRs (design checklist sections A, B, H). The risk register and the trade studies are reviewed with `peer-review-checklist-risk.md` and the independent classification assessment uses `peer-review-checklist-classification.md` (both exist). The SRR deck and the preliminary hazard analysis are reviewed with `peer-review-checklist-visual-product.md` and `peer-review-checklist-safety.md`, which Claude writes before the SRR package. The record pattern of `validate_docs.py` is `^peer-review-checklist-[a-z]+(-[a-z]+)*$` since 2026-09-25 (SEMP Appendix F item F-05; test `test_tools.PeerReviewRecordRuleTests.test_hyphenated_checklist_stem_is_accepted`), so the hyphenated stems `software-assurance` and `visual-product` are valid.

## 5. Return format

Agents return one `StructuredOutput` call with:

| Field | Content |
|---|---|
| `files_written` | Absolute paths of every file created or modified, including renders |
| `summary` | What was produced; commands run with exit status; renders inspected; confirmation that vector search preceded any manual search. A reviewer's summary also carries, one to one with the record front matter: `verdict` (`APPROVED` or `NEEDS CHANGES`), `checklist` (template stem), `product`, `product_commit`, `findings[]` (id, severity, location, description, fix, citation) and `measurements` (items checked, items answered No, findings by severity, findings fixed and deferred, re-review count as `iteration`, `effort_turns`, `effort_minutes`; SWE-089) |
| `citations_used` | Every SE HB, NPR 7123.1D, NPR 7150.2D, regulation or repo citation used, as written in the product |
| `charter_issues` | Contradictions, gaps or infeasible rules found in the charter or the governing process document |
| `open_questions` | Decisions the owner must make, missing inputs, absent scripts or checklists, headless paths that do not exist, a search tool outage |

Claude integrates the return: runs `tools/validate_docs.py` on the reviewer's record and checks its front matter against the returned fields, copies the verdict and finding counts into the review package, carries charter issues into the next review package's proposed-tailoring section, and carries open questions into the open-decisions list of the next package (charter §4 item 2 slide "TBD/TBR and open decisions"). Only the owner raises RFAs, at a review (charter §4 item 3).

## 6. Dispatch rules for Claude

1. One product, one author, one reviewer; the reviewer is a different invocation. Author to reviewer iterates at most three times per product; on the third NEEDS CHANGES, Claude stops and raises the item with the owner (heritage: `rustos/docs/sdp/methodology.md` §2).
2. Test cases for a module are authored before or in parallel with its implementation by a different invocation.
3. Claude runs `tools/validate_docs.py` and `tools/traceability.py` after integrating any returned files and before any review package is assembled.
4. A brief that would require an agent to edit the charter, a schema or a baselined item is not sent; the change goes through `CR-NNN` first.
5. A brief never asks for a GUI action, a screen capture or a macOS permission; if the only path is a GUI, the item goes to the owner as an open question (charter §11 rule 8).
6. Every brief carries the search-first hard rule of §1; a return whose summary shows manual search before vector search is sent back for rework (charter §11 rule 1).
7. Briefs are logged by product in the review record so the independence claim is auditable.

## 7. Differences from the rustos methodology

`rustos/docs/sdp/methodology.md` uses model-tier worker classes and a separate project-chief-engineer gate agent. cwht uses role blocks (author, reviewer, test author, analyst) without model tiers, and the owner is the gate. cwht keeps sprint records for software work (`docs/sprints/SW-NN-<module>.md`, 07 §3.4) and adds life-cycle review packages presented slide by slide with RFA/RID logs for the gates, the visual-closure rule, the headless-only rule, the search-first hard rule and the corpus citation rule.
